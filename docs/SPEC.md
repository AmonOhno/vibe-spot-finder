# Vibe Spot Finder アプリ仕様書

| 項目 | 内容 |
|---|---|
| バージョン | 0.2.0 |
| 最終更新 | 2026-10-28 |
| 対象 | Web ブラウザ（Chromium 系・Safari・Firefox の最新版） |

---

## 1. 概要

ユーザーが手元の **写真・動画** を読み込ませると、その色味や明暗から「雰囲気（Vibe）」を解析し、
**雰囲気の近い国内スポット** を **Google マップのリンク付き** で提案する Web アプリ。

### 1.1 目的
- 「この写真みたいな場所に行きたい」という漠然とした欲求を、具体的な行き先に変換する。
- 撮影場所が分からない SNS の写真・動画からでも、似た雰囲気の場所を見つけられるようにする。

### 1.2 想定ユーザー
- 旅行先・おでかけ先を探している人
- SNS で見かけた写真・動画の雰囲気に惹かれ、近い場所を知りたい人

### 1.3 スコープ（v0.1）
| 対象 | 対象外（将来検討 → §8） |
|---|---|
| 画像・動画 1 ファイルの解析 | 複数ファイルの同時解析 |
| ブラウザ内の色・テクスチャ特徴量と、Web 上の写真で学習した軽量モデルによる解析（§4.2） | 大規模な画像認識モデルによる被写体・シーン認識 |
| 静的データセット（全国 24 + 関東 2,000 スポット）からの推薦 | Google Places API 等による動的なスポット検索 |
| Google マップ検索 URL によるリンク | 地図埋め込み・経路案内 |

## 2. 画面構成

単一画面（SPA）。上から順に 3 つのセクションが表示される。

| # | セクション | 表示条件 | 主な要素 |
|---|---|---|---|
| 1 | 写真・動画を選ぶ | 常時 | ドロップゾーン、「ファイルを選択」ボタン、プライバシー注記、エラー表示、プレビュー、「雰囲気を解析する」「クリア」ボタン |
| 2 | 解析された雰囲気 | 解析完了後 | 主な雰囲気タグ（最大 3）、7 種の Vibe スコアバー、代表色パレット（最大 5 色）、解析フレーム数とサムネイル |
| 3 | 雰囲気が近いスポット | 解析完了かつ雰囲気を判定できた場合 | エリア絞り込み、スポットカード（名称・一致度・都道府県/エリア・説明・一致した雰囲気・Google マップリンク） |

### 2.1 状態遷移

```
idle ──(有効なファイル選択)──▶ ready ──(解析する)──▶ analyzing ──(成功)──▶ done
  ▲            │                  │                       │
  │      (無効なファイル)       (クリア)                (失敗: エラー表示)
  │            ▼                  │                       ▼
  └──── idle + エラー表示 ◀───────┘                     ready
done ──(別ファイル選択)──▶ ready（前回の結果・エリア選択はリセット）
done ──(クリア)──▶ idle
```

- `analyzing` 中はファイル選択・解析・クリアの各ボタンを無効化する。
- 解析完了時、解析結果セクションまで自動スクロールする。

## 3. 機能要件

| ID | 機能 | 内容 |

| F-01 | ファイル選択 | 「ファイルを選択」ボタンからファイルダイアログで 1 ファイルを選択できる |

| F-11 | クリア | 選択ファイル・解析結果・エラー・エリア選択をすべて初期化する |

## 4. 詳細仕様

### 4.1 入力ファイル

| 種別 | MIME タイプ | 上限サイズ |
|---|---|---|
| 画像 | `image/jpeg`, `image/png`, `image/webp`, `image/gif` | 20MB |
| 動画 | `video/mp4`, `video/webm`, `video/quicktime` | 200MB |

| 条件 | エラーメッセージ |
|---|---|
| 非対応形式 | 対応していないファイル形式です（JPEG / PNG / WebP / GIF / MP4 / WebM / MOV） |
| 画像サイズ超過 | 画像ファイルは 20MB 以下にしてください |
| 動画サイズ超過 | 動画ファイルは 200MB 以下にしてください |
| 画像デコード失敗 | 画像を読み込めませんでした |
| 動画デコード失敗 | 動画を読み込めませんでした |

※ 動画コーデックの対応可否はブラウザに依存する（例: Chromium は H.265/HEVC 非対応のことがある）。

### 4.2 雰囲気（Vibe）定義と算出方法

解析対象の各フレームを **長辺 96px に縮小** し、全ピクセルから特徴量を求める。
Vibe スコアは **学習済みモデル** と **ルール** の 2 つで算出し、画像のテクスチャ量に応じて混合する。

| Vibe ID | 表示名 |
|---|---|
| ocean | 海・水辺 |
| forest | 森・緑 |
| sunset | 夕焼け・ノスタルジック |
| night | 夜景・ネオン |
| snow | 雪・ミニマル |
| retro | レトロ・落ち着き |
| vivid | ビビッド・ポップ |

#### 4.2.1 学習済みモデル

- **特徴量（84 次元）**: `src/analysis/modelFeatures.ts`（学習側 `scripts/vibe_model/features.py` と同一定義）
  | 区分 | 次元 | 内容 |
  |---|---|---|
  | 色ヒストグラム | 29 | 有彩色（S ≥ 0.2, V ≥ 0.2）を色相 12 区分 × 明暗 2、無彩色を明るさ 4 段階、暗部（V < 0.2） |
  | 領域別ヒストグラム | 27 | 上・中・下の 3 領域ごとに 6 色相 + 明るい無彩色 + 暗い無彩色 + 暗部（空・地面の配置を捉える） |
  | 彩度 / 輝度ヒストグラム | 4 + 6 | 暗部を除く彩度 4 段階、輝度 6 段階 |
  | 統計量 | 7 | 輝度・彩度の平均と標準偏差、`R − B`、`G − (R + B) / 2`、カラフルネス（Hasler–Süsstrunk） |
  | テクスチャ | 5 | 輝度勾配（右・下隣との差）の平均、0.08 / 0.25 超の比率、上半分・下半分の平均 |
  | 比率特徴 | 6 | §4.2.2 の blueRatio / greenRatio / warmRatio / darkRatio / neonRatio / whiteRatio |
- **モデル**: 84 → 64（ReLU）→ 7（シグモイド）の多層パーセプトロン。出力は各 Vibe が写っている確率（0〜1）。
  重みは `src/analysis/vibeModelWeights.ts`（約 6,000 パラメータ）に同梱し、推論はブラウザ内で完結する（N-01）。
- **学習データ**: [Open Images Dataset](https://storage.googleapis.com/openimages/web/index.html)（Flickr 由来の Web 写真、
  人手検証済みの画像レベルラベル）から、Vibe ごとに対応するラベル（例: ocean = Sea / Beach / Coast…、
  sunset = Sunset / Dusk / Afterglow…、night = Night / Neon…、retro = Vintage / Antique / Monochrome…、
  vivid = Colorfulness / Graffiti / Amusement park…。対応表は `scripts/vibe_model/labels.py`）を持つ写真を
  最大 3,000 枚ずつ、どのラベルも持たない写真 5,000 枚とあわせて **計 21,800 枚** 取得して学習した。
  加えて、単色・グラデーション・図形のみの合成画像 4,000 枚に §4.2.2 のルールのスコアを教師として与えている。
  画像データはリポジトリに含めず、`scripts/vibe_model/README.md` の手順で再取得・再学習できる。
- **評価**（学習に使っていない実写 3,304 枚。閾値は §4.2.3 の 0.3）:
  | 指標 | v0.1 ルール | v0.2（本方式） |
  |---|---|---|
  | mAP（7 Vibe の平均適合率の平均） | 0.27 | **0.60** |
  | Top-1 正解率（最上位の Vibe が正解ラベルに含まれる率） | 0.36 | **0.67** |
  | マクロ F1（閾値 0.3） | 0.30 | **0.57** |
  | ラベルなし写真を「判定不可」にできた率 | 0.21 | **0.43** |

#### 4.2.2 ルール（v0.1 の方式）

| 特徴量 | 定義 |
|---|---|
| brightness | 輝度 `0.299R + 0.587G + 0.114B` の平均 |
| saturation | HSV の S の平均 |
| contrast | 輝度の標準偏差 |
| warmth | `R − B` の平均（-1〜1） |
| blueRatio | H: 180〜250°, S > 0.25, V > 0.2 の画素比率 |
| greenRatio | H: 70〜170°, S > 0.25, V > 0.2 の画素比率 |
| warmRatio | H: < 50° or > 330°, S > 0.45, V > 0.25 の画素比率 |
| darkRatio | V < 0.2 の画素比率 |
| neonRatio | V > 0.7 かつ S > 0.6 の画素比率 |
| whiteRatio | V > 0.85 かつ S < 0.12 の画素比率 |

`clamp(x)` を 0〜1 への切り詰め、`mid` を「brightness が 0.25〜0.8 なら 1、それ以外 0.3」とする。

| Vibe ID | スコア式 |
|---|---|
| ocean | `clamp(blueRatio × 1.6) × (brightness > 0.25 ? 1 : 0.4)` |
| forest | `clamp(greenRatio × 1.6)` |
| sunset | `clamp(warmRatio × 1.4) × mid` |
| night | `clamp(darkRatio × 1.2) × (0.6 + 0.4 × clamp(neonRatio × 5))` |
| snow | `clamp(whiteRatio × 1.5)` |
| retro | `clamp((0.5 − saturation) / 0.3) × clamp(warmth × 8) × mid` |
| vivid | `clamp((saturation − 0.45) / 0.35) × clamp(contrast × 4)` |

#### 4.2.3 混合と判定

- モデルは実写で学習しているため、単色・グラデーションのようにテクスチャのない画像は学習分布の外になる。
  輝度勾配の平均 `g` から `α = clamp((g − 0.005) / (0.03 − 0.005))` を求め、
  **スコア = α × モデル + (1 − α) × ルール** とする（実写の約 98% は `g ≥ 0.02`）。
- **主な雰囲気**: スコア **0.3 以上** の Vibe をスコア降順で最大 3 件。
- **代表色**: 各チャンネル上位 3bit で量子化した色の出現頻度上位 5 色。

### 4.3 動画のフレーム抽出
- 動画長を `d` として、`d × i / 6`（i = 1〜5）の 5 時点にシークしてフレームを取得する（先頭・末尾の暗転を避けるため両端を除外）。
- 特徴量（§4.2.1 の特徴ベクトル、§4.2.2 の色特徴量とも）は 5 フレームの **平均** を取り、平均値から Vibe スコアを算出する。
- 代表色は各フレームの代表色を順に集め、重複を除いた先頭 5 色とする。

### 4.4 スポット推薦
- スポットデータは静的データで、全国の代表スポット 24 件（`src/data/spots.ts`）と関東 1 都 6 県の 2,000 件（`src/data/kantoSpots.ts`）からなる。
- 各スポットは `id / name / prefecture / region / description / vibes（Vibe ごとの重み 0〜1）/ mapQuery?` を持つ。
- **一致度** = 解析 Vibe ベクトルとスポット Vibe ベクトルの **コサイン類似度**。
- 一致度 **0.2（20%）未満は提案しない**。一致度降順（同点は `id` 昇順）で **最大 6 件**。
- **一致した雰囲気**: `解析スコア × スポット重み` の寄与が大きい Vibe 上位 2 件。
- データ追加時の要件: 各 Vibe につき少なくとも 2 スポットが重み 0.8 以上を持つこと。全 6 エリアに 1 件以上あること。

#### 4.4.1 関東スポットデータ

- `scripts/spots/` のスクリプトで [Overture Maps](https://overturemaps.org/) の公開データ（S3）から生成する（手順は `scripts/spots/README.md`）。
  - **代表スポット（84 件）**: `scripts/spots/kanto_curated.py` に名称・説明・雰囲気の重みを手動で定義したもの（浅草寺、横浜中華街、日光東照宮など）。
    Overture のデータ上に同名の地物が想定の都県内に存在するものだけを採用する。
  - **自動生成（1,916 件）**: base テーマ（OpenStreetMap 由来）の名前付き地物から、海岸・岬・湖・滝・山・公園・庭園・社寺・史跡・展望地・
    スキー場・テーマパークなど観光向きの種別を判定し、種別ごとの基本の重みに名称中のキーワード（夜景・夕日・紅葉・桜・雪など）による補正を加える。
    知名度の目安（Wikidata の有無・面積・標高）の高い順に、種別ごとの上限を守って採用する。都県は行政区域ポリゴンで判定する。
- 関東スポットはすべて `region: '関東'`。Google マップの検索クエリは「名称 都県（＋住所タグの市区町村）」。
- 出典表記: 画面下部に「© OpenStreetMap contributors（Overture Maps Foundation 経由、ODbL）」を表示する。
- データ要件: 2,000 件、全件が関東 1 都 6 県、各都県 100 件以上（`src/data/spots.test.ts`）。

### 4.5 Google マップリンク
- 形式: `https://www.google.com/maps/search/?api=1&query=<URL エンコードしたクエリ>`
  （[Google Maps URLs](https://developers.google.com/maps/documentation/urls/get-started) の検索アクション。API キー不要）
- クエリ: `mapQuery` があればそれを、なければ `"<name> <prefecture>"` を使う。
- `target="_blank" rel="noopener noreferrer"` で新しいタブに開く。

## 5. 非機能要件

| ID | 区分 | 要件 |
|---|---|---|
| N-01 | プライバシー | 選択したファイルは **ブラウザ内でのみ処理** し、外部サーバーへ送信しない。解析中に外部オリジンへの通信を発生させない |
| N-02 | 性能 | 解析は縮小画像で行い、一般的な PC で画像 1 秒以内・動画 3 秒以内に完了すること |
| N-03 | レスポンシブ | 幅 375px（モバイル）で横スクロールが発生しないこと |
| N-04 | アクセシビリティ | 主要操作要素にアクセシブルネームを付与し、エラーは `role="alert"` で通知する |
| N-05 | ダークモード | `prefers-color-scheme: dark` に追従する |

## 6. アーキテクチャ

```
src/
├── App.tsx                 画面全体の状態管理（状態遷移 §2.1）
├── components/             表示コンポーネント（UploadArea / VibeSummary / SpotList）
├── analysis/
│   ├── media.ts            入力検証・フレーム抽出（DOM 依存）
│   ├── vibeAnalyzer.ts     色特徴量・Vibe スコアリング（モデルとルールの混合、純粋関数）
│   ├── modelFeatures.ts    学習モデル用の特徴ベクトル抽出（純粋関数）
│   ├── vibeModelWeights.ts 学習済みモデルの重み（自動生成）
│   ├── matcher.ts          スポット推薦（純粋関数）
│   └── types.ts            Vibe 定義・型
└── data/
    ├── spots.ts            スポットデータ・Google マップ URL 生成
    └── kantoSpots.ts       関東スポットデータ（自動生成）
scripts/
├── vibe_model/             学習データ取得・特徴量・学習（Python）
└── spots/                  関東スポットデータの生成（Python）
```

- 解析ロジック（`vibeAnalyzer.ts` / `matcher.ts`）は DOM に依存しない純粋関数とし、Vitest でユニットテストする。
- 将来 AI 解析（§8）に差し替えられるよう、UI は `AnalysisResult` 型にのみ依存する。
- 学習側（Python）とアプリ側（TS）の特徴量・スコアの一致は `src/analysis/modelFeatures.test.ts` で検証する。

## 7. テスト方針

| レイヤ | ツール | 対象 | 場所 |
|---|---|---|---|
| ユニット | Vitest | 解析・推薦・入力検証ロジック | `src/**/*.test.ts` |
| E2E | Playwright (Chromium) | 画面操作のシナリオ | `e2e/*.spec.ts` |
| 操作キャプチャ | Playwright video + 独自レポーター | 全 E2E テストの操作動画 | `e2e/recordings/` |

- E2E テストケースは [TEST_CASES.md](./TEST_CASES.md) で管理し、テストタイトル先頭に `TC-xx` を付けて 1 対 1 で対応させる。
- テスト用フィクスチャは `scripts/generate_fixtures.py` で生成し、`e2e/fixtures/` にコミットする。
- PR ごとに GitHub Actions で型チェック・ユニットテスト・E2E（リトライなしで全件パス必須）を実行し、Claude Code の `code-review` プラグインでレビューする（`.github/workflows/`）。
